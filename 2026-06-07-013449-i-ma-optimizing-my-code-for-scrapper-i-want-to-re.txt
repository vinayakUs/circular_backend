  def _fetch_with_retry(
      self,
      method: str,      # "GET" or "POST"
      url: str,
      *,
      max_retries: int,
      backoff_seconds: float,
      timeout: float,
      headers: dict | None = None,
      **kwargs,          # passes through data= for POST, etc.
  ) -> str:
      last_error: Exception | None = None
      for attempt in range(1, max_retries + 1):
          self.logger.info(f"Fetching {url} attempt={attempt}/{max_retries}")
          try:
              response = requests.request(
                  method, url, headers=headers, timeout=timeout, **kwargs
              )
              return response.text
          except Exception as exc:
              last_error = exc
              if attempt >= max_retries:
                  break
              sleep_seconds = backoff_seconds * attempt
              self.logger.warning(f"Retrying after error: {exc}")
              if sleep_seconds > 0:
                  time.sleep(sleep_seconds)
      raise last_error

● Good question. Here's what could go wrong if NSE switches from urllib to
  requests:

  1. Proxy behavior mismatch

  get_urllib_proxy_opener and get_requests_proxies both read the same env vars
  but build proxies differently — one builds a urllib OpenerDirector, the other
  returns a {"http": ..., "https": ...} dict. If NSE's proxy config is being
  used, the switch could result in different proxy routing. Both are working for
   their respective scrapers today, but that doesn't guarantee they're
  interchangeable.

  2. NSE India API may require specific request handling

  The NSE API (nseindia.com) is notoriously sensitive — it checks for specific
  cookie/header order, connection keep-alive, and may reject requests that look
  "wrong" (e.g., wrong User-Agent, missing Referer). urllib + opener has been
  working. requests sends data differently (chunked transfer encoding, different
   connection reuse) — could trigger different server behavior.

  3. Existing working code

  NSE works today. Any change carries risk of regression.

  4. Exception types

  - urllib raises URLError / HTTPError
  - requests raises RequestException

  The retry loop catches both with Exception, so technically it works. But if
  you ever wanted to handle timeout vs connection error differently, you'd need
  separate logic.

  ---

  response:
                  return json.loads(response.read().decode("utf-8"))
          except Exception as exc:
              last_error = exc
              if attempt >= self.max_retries:
                  break
              sleep(self.backoff_seconds * attempt)
      raise last_error

         self,
         url: str,
         *,
         max_retries: int,
         backoff_seconds: float,
         timeout: float,
         headers: dict,
         method: str = "GET",
         data: bytes | str | None = None,
     ) -> str:

         for attempt in range(1, max_retries + 1):
             self.logger.info("Fetching %s %s attempt=%s/%s", method, url,
     attempt, max_retries)

                 opener = get_urllib_proxy_opener(url)

❯ just a questio is get_urllib_proxy_opener and get_requests_proxies different  

● Yes, they do different things but read the same env vars.

  ┌─────────┬───────────────────────────────────┬──────────────────────────┐
  │         │      get_urllib_proxy_opener      │   get_requests_proxies   │
  ├─────────┼───────────────────────────────────┼──────────────────────────┤
  │         │ urllib.request.OpenerDirector     │ {"http": "http://...",   │
  │ Returns │ (installs handlers)               │ "https": "https://..."}  │
  │         │                                   │ (dict)                   │
  ├─────────┼───────────────────────────────────┼──────────────────────────┤
  │         │ urllib.request.urlopen() /        │ requests.get() /         │
  │ Used by │ opener.open()                     │ requests.post() via      │
  │         │                                   │ proxies= param           │
  ├─────────┼───────────────────────────────────┼──────────────────────────┤
  │ Same    │ CUSTOM_HTTP_PROXY,                │                          │
  │ env     │ CUSTOM_HTTPS_PROXY,               │ same three               │
  │ vars    │ PROXY_URL_PATTERNS                │                          │
  └─────────┴───────────────────────────────────┴──────────────────────────┘

  Same proxy logic, different output format — one builds a urllib opener, the
  other builds a requests-compatible dict. They can't be interchanged directly,
  which is why the unified plan switches everything to requests +
  get_requests_proxies.
