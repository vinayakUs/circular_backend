❯ explain more how watchdog finds which processor are pending                   

● The key insight is: a processor has "never run" for a circular if there's no 
  row in processing_tasks for that (circular_id, processor_name) pair.

  The flow:

  1. processor.run(record) is called for a circular
  2. It calls processor_repo.get_pending_circulars_for_processor(name, limit) —
  this does a LEFT JOIN to find circulars where pt.id IS NULL (no entry exists)
  OR pt.status IN ('FAILED', 'PENDING')
  3. If the circular qualifies, processor.process(record) runs4. Then
  mark_task_completed() inserts a row into processing_tasks with status = 
  'COMPLETED'

  So after all processors run successfully:

  circular_id | processor_name              | status
  ------------|---------------------------|----------
  uuid-123    | nse_applicability_processor | COMPLETED
  uuid-123    | designation_extractor_processor | COMPLETED

  If a processor never ran (e.g., circular was indexed but processor pipeline 
  never called for it):

  circular_id | processor_name              | status
  ------------|---------------------------|----------
  uuid-123    | nse_applicability_processor | COMPLETED
  -- designation_extractor_processor has NO ROW at all

  The watchdog's challenge: It needs to know which processors should have run.
  That's why we hardcode REGISTERED_PROCESSORS in the watchdog — it's the source
   of truth for "all expected processors."

  Watchdog's check for needs_process:

  REGISTERED_PROCESSORS = ["nse_applicability_processor",
  "designation_extractor_processor"]

  def needs_process(circular_id, db_pool) -> bool:
      # Count how many of these circular's processors are COMPLETED
      cursor.execute("""
          SELECT COUNT(*) FROM processing_tasks
          WHERE circular_id = %s          AND processor_name IN (%s, %s)
            AND status = 'COMPLETED'
      """, [circular_id, REGISTERED_PROCESSORS[0], REGISTERED_PROCESSORS[1]])

      completed = cursor.fetchone()[0]

      # If less than total registered, some never ran or failed
      return completed < len(REGISTERED_PROCESSORS)

  Tracing through your scenario (3 processors, only 2 completed):

  ┌────────────────┬────────────────────────────┐
  │ processor_name │ status in processing_tasks │
  ├────────────────┼────────────────────────────┤
  │ processor_1    │ COMPLETED                  │
  ├────────────────┼────────────────────────────┤
  │ processor_2    │ COMPLETED                  │
  ├────────────────┼────────────────────────────┤
  │ processor_3    │ NO ROW                     │
  └────────────────┴────────────────────────────┘

  completed = 1 (only processor_3 is the missing one... wait, 2 completed)
  len(REGISTERED_PROCESSORS) = 3
  2 < 3 → needs_process = TRUE

  The watchdog finds this circular and logs: needs_process=True.

  The limitation: The watchdog hardcodes the processor list. If you add a new
  processor, you must update REGISTERED_PROCESSORS in the watchdog. The
  processor pipeline code in pipeline.py also hardcodes the same list, so they
  stay in sync manually.

     The watchdog is a discovery-only mechanism. Every 5 minutes it scans the DB

     needs_process detection — requires comparing processing_tasks entries
     against the registered processor list:

     REGISTERED_PROCESSORS = ["nse_applicability_processor",
     "designation_extractor_processor"]

     def needs_process(circular_id, db_pool) -> bool:
         with db_pool.acquire() as conn:
             cursor = conn.cursor()
             placeholders = ",".join(["%s"] * len(REGISTERED_PROCESSORS))
             cursor.execute(f"""
                 SELECT COUNT(*) FROM processing_tasks
                 WHERE circular_id = %s
                   AND processor_name IN ({placeholders})
                   AND status = 'COMPLETED'
             """, [str(circular_id), *REGISTERED_PROCESSORS])
             completed = cursor.fetchone()[0]
             return completed < len(REGISTERED_PROCESSORS)

● Watchdog Flow — Complete Explanation

  What It Does

  The watchdog is a discovery-only mechanism. Every time it runs, it queries the
   DB for circulars that are "stuck" — meaning they need processing at some
  stage but haven't completed it. It logs what it finds, then exits. It does not
   trigger any processing.

  The Flow

  watchdog_flow (manual trigger or schedule)
      │
      └── find_incomplete_circulars()  [Prefect task]
               │
               └── SQL query → returns list of circulars with flags
               │
               └── For each circular: log id, source, status, flags

  The SQL Query (the core of it)

  WITH processor_status AS (
      -- For each circular, count how many processors COMPLETED
      SELECT
          pt.circular_id,
          COUNT(*) FILTER (WHERE pt.status = 'COMPLETED') AS completed_count
      FROM processing_tasks pt
      WHERE pt.processor_name IN ('nse_applicability_processor',
  'designation_extractor_processor')
      GROUP BY pt.circular_id
  ),
  notified AS (
      -- For each circular, check if it was emailed (circular_uuid stored in 
  JSONB variables)
      SELECT (variables->>'circular_uuid')::uuid AS circular_uuid
      FROM notification_logs
      WHERE template_name = 'circular_notification.html'
        AND status = 'SENT'
        AND variables->>'circular_uuid' IS NOT NULL
  )
  SELECT
      c.id,
      c.circular_id,
      c.source,
      c.status,
      c.detected_at,
      -- Flag: needs_index    CASE WHEN c.status = 'FETCHED' AND c.es_indexed_at
   IS NULL THEN TRUE ELSE FALSE END AS needs_index,
      -- Flag: needs_process
      CASE WHEN c.status = 'FETCHED'
   AND (ps.completed_count IS NULL OR ps.completed_count < 2) THEN TRUE ELSE
  FALSE END AS needs_process,
      -- Flag: needs_notify
      CASE WHEN c.status = 'FETCHED'
       AND c.detected_at >= NOW() - INTERVAL '24 hours'
       AND n.circular_uuid IS NULL THEN TRUE ELSE FALSE END AS needs_notify
  FROM circulars c
  LEFT JOIN processor_status ps ON c.id = ps.circular_id
  LEFT JOIN notified n ON c.id = n.circular_uuid
  WHERE
      (c.status = 'FETCHED' AND c.es_indexed_at IS NULL)
      OR (c.status = 'FETCHED' AND (ps.completed_count IS NULL OR
  ps.completed_count < 2))
      OR (c.status = 'FETCHED' AND c.detected_at >= NOW() - INTERVAL '24 hours'
  AND n.circular_uuid IS NULL)
  ORDER BY c.detected_at ASC
  LIMIT 100

  The Three Flags Explained

  needs_index — status = 'FETCHED' AND es_indexed_at IS NULL
  - The PDF was downloaded (FETCHED) but never indexed to Elasticsearch
  - Someone needs to run the ES indexer for this circular

  needs_process — status = 'FETCHED' AND completed_count < 2
  - The PDF was downloaded- But not all registered processors have run to
  completion
  - completed_count IS NULL → no processor ever ran for this circular
  - completed_count < 2 → some ran but not all (or some failed)
  - Hardcoded count of 2 = number of registered processors

  needs_notify — status = 'FETCHED' AND detected_at >=24h ago AND not in
  notification_logs
  - The circular is fresh enough to notify about (within 24h of discovery)
  - AND it hasn't been emailed yet
  - detected_at check prevents spamming about old circulars

  The processing_tasks Table Role

  This table is the source of truth for processor progress. Each row = one
  processor run for one circular.

  ┌────────────────┬────────────────────────────────────────────────────┐
  │     column     │                      meaning                       │
  ├────────────────┼────────────────────────────────────────────────────┤
  │ circular_id    │ which circular                                     │
  ├────────────────┼────────────────────────────────────────────────────┤
  │ processor_name │ which processor (e.g. nse_applicability_processor) │
  ├────────────────┼────────────────────────────────────────────────────┤
  │ status         │ PENDING / COMPLETED / FAILED                       │
  └────────────────┴────────────────────────────────────────────────────┘

  The watchdog checks: for this circular, how many processors have status = 
  'COMPLETED'? If less than total registered → needs_process = TRUE.

  Output Example

  When the watchdog runs, it logs:

  Watchdog found 3 incomplete circulars:
    circular_id=CMPT74594 source=NSE status=FETCHED needs_index=True
  needs_process=False needs_notify=False circular_id=SEBI/CIR/2024/12
  source=SEBI status=FETCHED needs_index=False needs_process=True
  needs_notify=True
    circular_id=NSE/CM/2024/55 source=NSE status=FETCHED needs_index=True
  needs_process=True needs_notify=False

  Each line tells you exactly which stages each circular needs — you then decide
   what to do about it.

  ⎿  ⧉ Selected 1 lines from prefect_dags/tasks/watchdog_tasks.py in Visual Studio Code

● Here's the full query with each part explained:

  WITH processor_status AS (
      -- For each circular, count how many of its processors completed 
  successfully
      SELECT
          pt.circular_id,
          COUNT(*) FILTER (WHERE pt.status = 'COMPLETED') AS completed_count
      FROM processing_tasks pt
      WHERE pt.processor_name IN ('nse_applicability_processor',
  'designation_extractor_processor')
      GROUP BY pt.circular_id
  ),
  notified AS (
      -- For each circular, check if an email was sent (circular_uuid stored in 
  JSONB variables)
      SELECT (variables->>'circular_uuid')::uuid AS circular_uuid
      FROM notification_logs
      WHERE template_name = 'circular_notification.html'
        AND status = 'SENT'
        AND variables->>'circular_uuid' IS NOT NULL
  )
  SELECT
      c.id,
      c.circular_id,
      c.source,
      c.status,
      c.detected_at,
   -- needs_index: PDF exists but not in Elasticsearch
      CASE WHEN c.status = 'FETCHED' AND c.es_indexed_at IS NULL THEN TRUE ELSE
  FALSE END AS needs_index,
      -- needs_process: PDF exists but not all processors ran to completion
      CASE WHEN c.status = 'FETCHED' AND (ps.completed_count IS NULL OR
  ps.completed_count < 2) THEN TRUE ELSE FALSE END AS needs_process,
      -- needs_notify: PDF exists, discovered< 24h ago, and not emailed yet
      CASE WHEN c.status = 'FETCHED' AND c.detected_at >= NOW() - INTERVAL '24 
  hours' AND n.circular_uuid IS NULL THEN TRUE ELSE FALSE END AS needs_notify
  FROM circulars c
  LEFT JOIN processor_status ps ON c.id = ps.circular_id
  LEFT JOIN notified n ON c.id = n.circular_uuid
  WHERE
      (c.status = 'FETCHED' AND c.es_indexed_at IS NULL)
      OR (c.status = 'FETCHED' AND (ps.completed_count IS NULL OR
  ps.completed_count < 2))
      OR (c.status = 'FETCHED' AND c.detected_at >= NOW() - INTERVAL '24 hours'
  AND n.circular_uuid IS NULL)
  ORDER BY c.detected_at ASC
  LIMIT 100

  The three CTE parts:

  ┌──────────────────┬───────────────────────────────────────────────────────┐
  │       CTE        │                     What it does                      │
  ├──────────────────┼───────────────────────────────────────────────────────┤
  │ processor_status │ Groups processing_tasks by circular, counts COMPLETED │
  │                  │  rows per circular                                    │
  ├──────────────────┼───────────────────────────────────────────────────────┤
  │                  │ Finds circulars that have a SENT entry in             │
  │ notified         │ notification_logs (by extracting circular_uuid from   │
  │                  │ JSONB variables column)                               │
  └──────────────────┴───────────────────────────────────────────────────────┘

  The WHERE clause — a circular is "incomplete" if ANY of these are true:
  - It needs indexing (FETCHED but es_indexed_at IS NULL)
  - It needs processing (FETCHED but completed_count < 2 or NULL)
  - It needs notifying (FETCHED, discovered < 24h ago, not in notification_logs)
