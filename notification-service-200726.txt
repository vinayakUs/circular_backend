● Here's my analysis of your notification service. It's a solid, well-structured
  design (clean separation between EmailService, the log repository, the
  mention repository, and a cron-friendly worker), but there are several real
  bugs and risks worth addressing.

  🔴 Critical

  1. notification_worker.py is duplicated — the second main() is broken
  The file defines main() and if __name__ == "__main__" twice (lines 79–130,
  then 132–171). The second main() (line 132) references a module-level logger
  that is never defined at module scope → NameError if ever called.

  - When run as python -m services.notification_worker, the first if __name__
  block calls the correct main() and sys.exit() terminates before the duplicate
  is reached — so it works by luck.
  - But if anything imports this module and calls main(), both def main()
  execute, the broken one wins (redefinition), and it crashes. Delete lines
  131–171.

  2. HTML/script injection in emails (no Jinja2 autoescaping)
  _render_template uses Template(...) without autoescape=True. The mention email
  renders user-controlled comment text (row["text"], mentioned_by) straight
  into HTML. A comment containing <script> or malicious markup gets injected raw
  into recipients' inboxes. For a compliance-facing product this is a genuine
  XSS/phishing vector.
  from jinja2 import Environment, select_autoescape
  # render with autoescape enabled for .html templates

  🟠 Correctness / reliability

  3. Duplicate-send race condition. get_pending_circulars() de-dupes against
  logs where status = 'SENT'. There's no lock and PENDING isn't excluded. With a
  5-min cron, if a run overruns the interval two workers overlap and both send
  the same circular (neither sees the other's SENT yet). Consider a DB-level
  advisory lock or a unique constraint on (template, circular_uuid) for SENT, or
  claim rows atomically.

  4. Mention failures are terminal; circular failures aren't — inconsistent.
  mark_failed sets mention status to FAILED, and list_pending() only returns
  PENDING, so a failed mention is never retried. Circulars, by contrast, are
  retried (FAILED isn't in the "notified" set). Neither path has retry/backoff.
  Decide on one policy; add a retry count.

  5. Dedup key only exists on the BCC path. get_notified_circular_ids matches on
  variables->>'circular_uuid', but send_circular_notification (lines 78–85)
  doesn't put circular_uuid in its variables — only the BCC methods do. The
  worker uses the BCC path so it's fine today, but the single-recipient method
  would never be de-duplicated.

  6. One bad template aborts the whole run. In send_pending_notifications,
  _render_template isn't wrapped in try/except and runs inside the worker's
  outer try, so a single missing/broken template returns exit code 2 and blocks
  all pending circulars. Wrap per-item so one failure only fails that item.

  🟡 Security / hygiene

  7. Bcc header is written into the message. _send_bcc_email sets msg["BCC"] = 
  ", ".join(recipients) and passes to_addrs. Delivery is handled by to_addrs;
  the header is redundant and, if the relay doesn't strip it, leaks the full 
  recipient list. Also there's no To: header at all, which some filters reject.
  Drop the Bcc header and set To: undisclosed-recipients:; or the from address.

  8. Verbose PII logging. get_pending_circulars and get_notified_circular_ids
  emit large [NOTIFICATION DEBUG] blocks at INFO level, logging recipient emails
  and content. This looks like leftover debugging — drop to DEBUG or remove;
  avoid logging emails.

  9. Hardcoded domain. https://abc.com/... is baked into
  send_mention_notification and get_pending_circulars. Move the base URL to
  Config.

  🟢 Minor / efficiency

  - New SMTP connection + login per circular. send_pending_notifications
  opens/authenticates a fresh SMTP session for every circular. Fine at low
  volume; batch over one connection if volume grows.
  - Plaintext creds if SMTP_USE_TLS=false. Login happens regardless of TLS —
  credentials go cleartext when TLS is off. Consider requiring TLS when a
  password is set.
  - Redundant import logging inside get_pending_circulars /
  get_notified_circular_ids (already imported at module top in the repo).

  dead/broken duplicate in the worker) and #2 (enable Jinja2 autoescaping) —
  both are quick and both are real. I can put together a plan if you'd like to
  tackle a batch.
